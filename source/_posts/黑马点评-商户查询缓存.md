# 什么是缓存

缓存就是数据交换的缓冲区(称作Cache),是存储数据的临时地方，一般读写性能较高<!--more-->

## 缓存的作用

- 降低后端负载
- 提高读写效率，降低响应时间

## 缓存的成本

- 数据一致性成本
- 代码维护成本
- 运维成本

        }

        //4.不存在，根据id查询数据库
        Shop shop = getById(id);

        //5.不存在，返回错误
        if (shop == null){
            return Result.fail("店铺不存在!");
        }

        //6.存在，写入redis
        stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop));

        //7.返回
        return Result.ok(shop);
    }
```

一般来说应该用hash缓存格式最好，这里用的是string缓存的，思维逻辑如下：

- 从redis查询商铺缓存
- 判断是否存在
  - 存在，直接返回
- 不存在，根据id查询数据库
- 不存在，返回错误
- 存在，写入redis
- 返回

其中string类型存储的是一个json格式的数据，因此我们需要用JSONUtil.toBean将获取的json数据转换成shop.class数据存储起来

        //2.如果缓存不为空，直接返回
        if (StrUtil.isNotBlank(typeJson)) {
            List<ShopType> shopTypeList = JSONUtil.toList(typeJson, ShopType.class);
            return Result.ok(shopTypeList);
        }
        //为空，查询
        List<ShopType> shopTypeList = query().orderByAsc("sort").list();

    }
```

**思路梳理：**

- 从redis中查询类型缓存是否存在`String typeJson = stringRedisTemplate.opsForValue().get(key);`
- 如果redis缓存中存在数据，那么直接从redis中获取的缓存反序列化为对应的ShopType.class并且存储起来`List<ShopType> shopTypeList = JSONUtil.toList(typeJson, ShopType.class);`然后返回给前端
- 如果redis缓存为空，那么通过mybatis-plus语句的quer()函数通过sort列进行升序排序获取list集合`List<ShopType> shopTypeList = query().orderByAsc("sort").list();`
- 最后将数据库信息保存到缓存中`stringRedisTemplate.opsForValue().set(key,JSONUtil.toJsonStr(shopTypeList));`并且通过序列化器转换成json格式存储到redis缓存中，并且返回数据给前端

# 缓存更新策略

|              | 内存淘汰                                                     | 超时剔除                                                     | 主动更新                                   |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------ |
| **说明**     | 不用自己维护，利用Redis的内存淘汰机制，当内存不足时自动淘汰部分数据。下次查询时更新缓存 | 给缓存数据增加TTL时间，到期后自动删除缓存。下次查询时更新缓存 | 编写业务逻辑，在修改数据库的同时，更新缓存 |
| **一致性**   | 差                                                           | 一般                                                         | 好                                         |
| **维护成本** | 无                                                           | 低                                                           | 高                                         |

**业务场景：**

- 低一致性需求：使用内存淘汰机制。例如店铺类型的查询缓存
- 高一致性需求：主动更新，并以超时剔除作为兜底方案。例如店铺详情查询

![image-20260224222206985](/images/黑马点评/image-20260224222206985.png)

操作缓存和数据库时有3个问题需要考虑：

1、删除缓存还是更新缓存？

- 更新缓存：每次更新数据库都更新缓存，无效写操作比较多(x)
- 删除缓存：更新数据库时让缓存失效，查询时再更新缓存(√)

2、如何保证缓存与数据库的操作的同时成功或失败？

- 单体系统，将缓存与数据库操作放在一个事物
- 分布式系统，利用TCC等分布式事务方案

3、先操作缓存还是先操作数据库？

- 先删除缓存，再操作数据库<img src="C:\Users\逸杰\AppData\Roaming\Typora\typora-user-images\image-20260224223508996.png" alt="image-20260224223508996" style="zoom: 50%;" />
  - 一般来说是线程1，删除缓存->更新数据库，线程2，查询缓存未命中，查询数据库->写入缓存
  - 但是当用户多的时候我们会出现线程1刚删除缓存，线程2就来查询缓存了，未命中查询数据库，然后写入缓存，这就导致缓存删除失败，这个时候更新数据库也只是更新了数据库没有更新缓存，缓存依旧是旧的数据，存在一致性的问题
- 先操作数据库，再删除缓存<img src="C:\Users\逸杰\AppData\Roaming\Typora\typora-user-images\image-20260224224155723.png" alt="image-20260224224155723"  />
  - 正常情况应该是线程2：更新数据库->删除缓存，然后线程1：查询缓存，未命中，查询数据库->写入缓存
  - 但是有时会再缓存失效的时候，线程1来查询缓存，未命中，查询数据库，这时线程2的数据更新数据库->删除缓存，之后线程1才执行写入缓存就会使刚刚查询数据库的数据，**但是这种可能性是比较低的**

# 缓存穿透

**缓存穿透**是指客户端请求的数据在**缓存中和数据库中都不存在**，这样缓存永远不会生效，这些请求都会打到数据库

常见的解决方案有两种：

- 缓存空对象：同key不存在反复请求
  - <img src="C:\Users\逸杰\AppData\Roaming\Typora\typora-user-images\image-20260224232357568.png" alt="image-20260224232357568" style="zoom:25%;" />
  - 优点：实现简单，维护方便
  - 缺点
    - 额外的内存消耗（容易有很多垃圾缓存(null)）
    - 可能造成短期的不一致（新增数据的时候主动添加缓存覆盖之前的null缓存）
- 布隆过滤：不同key不存在海量反复请求
  - <img src="C:\Users\逸杰\AppData\Roaming\Typora\typora-user-images\image-20260224232827456.png" alt="image-20260224232827456" style="zoom: 50%;" />
  - 优点：
    - 内存占用较少，没有多余key
  - 缺点：
    - 实现复杂
    - 存在误判可能

![image-20260224233216352](/images/黑马点评/image-20260224233216352.png)

- 增强id的复杂度，避免被猜测id规律
- 做好数据的基础格式校验
- 加强用户权限校验
- 做好热点参数的限流

# 缓存雪崩

**缓存雪崩**是指在同一时段大量的缓存key同时失效或者Redis服务宕机，导致大量请求到达数据库，带来巨大压力![image-20260225163402998](/images/黑马点评/image-20260225163402998.png)

 **解决方案：**

- 给不同的key的ttl添加随机值
- 利用Redis集群提高服务的可用性(哨兵机制)
- 给缓存业务添加降级限流策略
- 给业务添加多级缓存

# 缓存击穿

**缓存击穿问题**也叫热点key问题，就是一个**被高并发访问**并且**缓存重建业务较复杂**的key突然失效了，无数的请求访问会在瞬间给数据库带来巨大的冲击。![image-20260225170407725](/images/黑马点评/image-20260225170407725.png)

一句话：一个热点 key 突然过期 / 被删除，大量请求瞬间直接打到数据库。

常见的解决方案有2种：

- 互斥锁
- 逻辑过期

![image-20260225172223441](/images/黑马点评/image-20260225172223441.png)

| 解决方案 | 优点                                     | 缺点                                     |
| -------- | ---------------------------------------- | ---------------------------------------- |
| 互斥锁   | 没有额外的内存消耗、保证一致性、实现简单 | 线程需要等待，性能受影响、可能有死锁风险 |
| 逻辑过期 | 线程无需等待，性能较好                   | 不保证一致性、有额外内存消耗、实现复杂   |

## 基于互斥锁方式解决缓存击穿问题

需求：修改根据id查询商铺的业务，基于互斥锁方式来解决缓存击穿问题

![image-20260225174755817](/images/黑马点评/image-20260225174755817.png)

```ShopServiceImpl.java
	@Override
    public Result queryById(Long id) {
        // 缓存穿透
        //Shop shop = queryWithPassThrough(id);

        //互斥锁解决缓存击穿
        Shop shop = queryWithMutex(id);
        if (shop == null){
            return Result.fail("店铺不存在！");
        }

        //7.返回
        return Result.ok(shop);
    }
    
    /**
     * 缓存击穿
     * @param id
     * @return
     */
    public Shop queryWithMutex(Long id){
        String key = CACHE_SHOP_KEY + id;
        //1.从redis查询商铺缓存
        String shopJson = stringRedisTemplate.opsForValue().get(key);

        //2.判断是否存在
        if(StrUtil.isNotBlank(shopJson)){
            //3.存在，直接返回
            return JSONUtil.toBean(shopJson, Shop.class);
        }
        // 判断命中的是否是空值
        if(shopJson != null){
            return null;
        }

        //4.实现缓存重建
        //4.1.获取互斥锁
        String lockkey = LOCK_SHOP_KEY + id;
        Shop shop = null;
        try {
            boolean isLock = tryLock(lockkey);
            //4.2.判断是否获取成功
            if (!isLock){
                //4.3.失败，则休眠并重试
                Thread.sleep(50);
                return queryWithMutex(id);
            }


            //4.4.成功，根据id查询数据库
            shop = getById(id);
            //模拟重建的延时
            Thread.sleep(200);
            //5.不存在，返回错误
            if (shop == null){
                stringRedisTemplate.opsForValue().set(key,"",CACHE_NULL_TTL,TimeUnit.MINUTES);
                return null;
            }

            //6.存在，写入redis
            stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop),CACHE_SHOP_TTL, TimeUnit.MINUTES);
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }finally {
            //7.释放互斥锁
            unLock(lockkey);
        }

        //8.返回
        return shop;
    }
    /**
     * 缓存穿透
     * @param id
     * @return
     */
    public Shop queryWithPassThrough(Long id){
        String key = CACHE_SHOP_KEY + id;
        //1.从redis查询商铺缓存
        String shopJson = stringRedisTemplate.opsForValue().get(key);

        //2.判断是否存在
        if(StrUtil.isNotBlank(shopJson)){
            //3.存在，直接返回
            return JSONUtil.toBean(shopJson, Shop.class);
        }
        // 判断命中的是否是空值
        if(shopJson != null){
            return null;
        }
        //4.不存在，根据id查询数据库
        Shop shop = getById(id);

        //5.不存在，返回错误
        if (shop == null){
            stringRedisTemplate.opsForValue().set(key,"",CACHE_NULL_TTL,TimeUnit.MINUTES);
            return null;
        }

        //6.存在，写入redis
        stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop),CACHE_SHOP_TTL, TimeUnit.MINUTES);

        //7.返回
        return shop;
    }

    /**
     * 尝试获取锁
     * @param key
     * @return
     */
    private boolean tryLock(String key){
        Boolean flag = stringRedisTemplate.opsForValue().setIfAbsent(key, "1", 10, TimeUnit.SECONDS);
        return BooleanUtil.isTrue(flag);
    }

    /**
     * 释放锁
     * @param key
     */
    private void unLock(String key){
        stringRedisTemplate.delete(key);
    }
```

## 互斥锁解决缓存击穿的步骤

- 直接通过调用queryWithMutex()函数提交商铺id

- 在queryWithMutex()函数中从redis查询商铺缓存
- 判断这个缓存是否存在，如果存在直接返回缓存即可
- 如果缓存不存在，由于我们前面缓存穿透设置了空字符串，所以需要进行判断返回null值
- 进行缓存重建
  - 首先是获取互斥锁，因此我们需要设置锁的key并且shop初始化设置为null
  - 通过前面设置锁的key设置互斥锁
    - tryLock中通过setIfAbsent函数设置互斥锁并且设置根据实际情况设置互斥锁的时间，setIfAbsent的返回值是Boolean类型的数据，而我们需要拆箱如果直接返回值可能会出现空值的问题，所以我们应该用hutool依赖的`BooleanUtil.isTrue(flag)`返回boolean的值
  - 通过返回的tryLock值，来判断是否获取互斥锁成功
    - 如果创建互斥锁失败，说明已经有个进程在使用互斥锁了，这个时候就需要该进程休眠一段时间使用`Thread.sleep(50);`休眠50毫秒并且反复执行递归(这里存在问题，如果**递归太多会导致堆溢出**)
  - 如果是第一次创建互斥锁，那么就会去查询数据库，如果数据库不存在这个数据，就设置null值防止缓存雪崩
  - 如果数据存在就写入缓存，最终释放互斥锁，返回数据

为了实现基于逻辑过期方式解决缓存击穿问题，我们需要设置逾期时间，这里使用Object类主要是为了复用这个数据。

```ShopServiceImpl.java
    public void saveShop2Redis(Long id, Long expireSeconds) throws InterruptedException {
        //1.查询店铺数据
        Shop shop = getById(id);
        Thread.sleep(200);
        //2.封装逻辑过期时间
        RedisData redisData = new RedisData();
        redisData.setData(shop);
        redisData.setExpireTime(LocalDateTime.now().plusSeconds(expireSeconds));

        //3.写入redis   stringRedisTemplate.opsForValue().set(CACHE_SHOP_KEY+id,JSONUtil.toJsonStr(redisData));
    }

```

saveShop2Redis用于拼接数据和过期时间

```ShopServiceImpl.java
    private static final ExecutorService CACHE_REBUILD_EXECUTOR = Executors.newFixedThreadPool(10);

    public Shop queryWithLogicExpire(Long id){
        String key = CACHE_SHOP_KEY + id;
        //1.从redis查询商铺缓存
        String shopJson = stringRedisTemplate.opsForValue().get(key);

        //2.判断是否存在
        if(StrUtil.isBlank(shopJson)){
            //3.未命中，返回空
            return null;
        }

        //4.命中，需要把json反序列化为对象
        RedisData redisData = JSONUtil.toBean(shopJson, RedisData.class);
        Shop shop = JSONUtil.toBean((JSONObject)redisData.getData(), Shop.class);
        LocalDateTime expireTime = redisData.getExpireTime();

        //5.判断是否过期
        if (expireTime.isAfter(LocalDateTime.now())){
            //5.1.未过期，直接返回店铺信息
            return shop;
        }
        //5.2.已过期，需要缓存重建
        //6.缓存重建
        //6.1.获取互斥锁
        String lockKey = LOCK_SHOP_KEY + id;
        boolean isLock = tryLock(lockKey);

        //6.2.判断是否获取成功
        if (isLock){
            // 成功.开启独立线程，实现缓存重建
            CACHE_REBUILD_EXECUTOR.submit(()->{
                try {
                    //重建缓存
                    this.saveShop2Redis(id,20L);
                } catch (Exception e) {
                    throw new RuntimeException(e);
                }finally {
                    //释放锁
                    unLock(lockKey);
                }
            });
        }

        //6.4.返回过期的商铺信息
        return shop;
    }
```

其中`private static final ExecutorService CACHE_REBUILD_EXECUTOR = Executors.newFixedThreadPool(10);`是创建一个包含10个线程的线程池。

**思想如下**：

- 从redis中查询商铺的缓存并且判断是否存在，如果未命中返回空值

- 如果命中，我们就对缓存的数据反序列化转成`RedisData.java`

  - 由于`RedisData`类的data属性属于Object可以强行转换为JSONObject属性，通过`JSONUtil.toBean()`方式转换成Shop属性

- 根据缓存的过期时间，通过`isAfter()`函数与当前时间做比较，如果未过期直接返回店铺信息

  - 如果已过期，我们需要缓存重建，获取互斥锁

    - 如果互斥锁获取成功，开启独立线程，实现缓存重建

    - ```java
                  CACHE_REBUILD_EXECUTOR.submit(()->{
                      try {
                          //重建缓存
                          this.saveShop2Redis(id,20L);
                      } catch (Exception e) {
                          throw new RuntimeException(e);
                      }finally {
                          //释放锁
                          unLock(lockKey);
                      }
                  });
      ```

# 缓存工具封装

基于StringRedisTemplate封装一个缓存工具类，满足下列需求：

- 方法1：将任意JAVA对象序列化为json并存储在string类型的key中，并且可以设置TTL过期时间
- 方法2：将任意JAVA对象序列化为json并存储在string类型的key中，并且可以设置逻辑过期时间，用于处理缓存击穿问题
- 方法3：根据指定的key查询缓存，并反序列化为指定类型，利用缓存空值的方式解决缓存穿透问题
- 方法4：根据指定的key查询缓存，并反序列化为指定类型，需要利用逻辑过期解决缓存击穿问题

```CacheClient.java
@Slf4j
@Component
public class CacheClient {

    private final StringRedisTemplate stringRedisTemplate;

    public CacheClient(StringRedisTemplate stringRedisTemplate){
        this.stringRedisTemplate = stringRedisTemplate;
    }

    /**
     * 设置过期时间
     * @param key
     * @param value
     * @param time

     * @return

            //3.未命中，返回空

                    //写入redis
                    this.setWithLogicalExpire(key, r1, time, unit);
                } catch (Exception e) {
                    throw new RuntimeException(e);
                }finally {
                    //释放锁
                    unLock(lockKey);
                }
            });

        return r;

    private boolean tryLock(String key){

    }

     */
    private void unLock(String key){

采用泛型得形式接受值，接受结果如下：

- `<R,ID>`:定义了2个泛型
- `keyPrefix`:关键词的前缀
- `id`:传递的参数类型
- `Class<R> type`：传递类
- `Function<ID,R> dbFallback`：这里传递的是函数语句，主要是数据返回的函数比如`getById()`，接受ID的值，返回R的值

- `TimeUnit unit`：用于传递TimeUnit的值，比如`TimeUnit.MINUTES`

### 逻辑梳理

- 先从从redis查询缓存
- 通过`isNotBlank()`判断缓存是否存在，存在则直接返回`return JSONUtil.toBean(json, type);`
- 如果传递的是空字符串就返回null
- 如果不存在缓存就根据id查询数据`R r = dbFallback.apply(id);`
  - R是接受任意类型的值，`apply(id)`是运行这个函数，并且传递对应的值
- 如果数据库不存在数据就设置缓存空值并且返回null
- 存在则写入redis
