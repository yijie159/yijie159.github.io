# 全局唯一ID<!--more-->

每个店铺都可以发布优惠券：

当用户抢购时，就会生成订单并保存到tb_voucher_order这张表中，而订单表如果使用数据库自增ID就会存在一些问题：

- id的规律性太明显
- 受单表数据量的限制

全局ID生成器，是一种分布式系统下用来生成全局唯一ID的工具，一般要满足下列特性：

- 唯一性
- 高可用
- 高性能
- 递增性
- 安全性

为了增加ID的安全性，我们可以不直接使用Redis自增的数值，而是拼接一些其他信息：

![image-20260302150649390](/images/黑马点评/image-20260302150649390.png)

ID的组成部分：

- 符号位：1bit，永远为0
- 时间戳：31bit，以秒为单位，可以使用69年
- 序列号：32bit，秒内的计数器，支持每秒产生2^32个不同ID

```RedisIdWork.java
@Component
public class RedisIdWorker {

    /**
     * 时间戳起始点
     */
    private static final long BEGIN_TIMESTAMP = 1640995200L;
    /**
     * 序列号位数
     */
    private static final int COUNT_BITS = 32;


    private StringRedisTemplate stringRedisTemplate;

    public RedisIdWorker(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    public long nextId(String keyPrefix) {
        // 1.生成时间戳
        LocalDateTime now = LocalDateTime.now();
        long nowEpochSecond = now.toEpochSecond(ZoneOffset.UTC);
        long timestamp = nowEpochSecond - BEGIN_TIMESTAMP;

        // 2.生成序列号
        // 2.1.获取当前日期，精确到天
        String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));
        // 2.2.自增长
        long count = stringRedisTemplate.opsForValue().increment("icr" + keyPrefix + timestamp + ":" + date);

        // 3.拼接并返回
        return timestamp << COUNT_BITS | count;
    }
}

```

## 思想(1)：

- 定义一个初始化的时间戳
- 通过有参构造注入依赖
- 生成时间戳
  - 通过`LocalDateTime now = LocalDateTime.now();`获取到当前时间，并且通过`now.toEpochSecond(ZoneOffset.UTC);`转化成long型的数据，相加减获取到时间长度这样时间戳就有了
- 生成序列号
  - 通过`String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));`获取当前日期，精确到天
  - 我们需要对序列号进行自增长的操作，那么`stringRedisTemplate.opsForValue().increment("icr" + keyPrefix + timestamp + ":" + date);`使用的`increment()`函数就会自增长
    - 如果 `key` 不存在，会先将其值初始化为 `0`，再执行 `+1`，返回结果为 `1`；
- 拼接并返回
  - 返回的数据通过左位运算32为将其清0，与自增长(count)做或运算(有1为1)得出正确的数据

    private ExecutorService es = Executors.newFixedThreadPool(500);

    @Test
    void testIdWorker() throws InterruptedException {
        CountDownLatch latch = new CountDownLatch(300);

        Runnable task = () -> {
            for (int i = 0; i < 100; i++) {
                long id = redisIdWorker.nextId("order");
                System.out.println("id = " + id);
            }
            latch.countDown();
        };
        long begin = System.currentTimeMillis();

        for (int i = 0; i < 300; i++) {
            es.submit(task);
        }

        latch.await();
        long end = System.currentTimeMillis();
        System.out.println("time =" + (end - begin));
    }
```

## 思路(2):

- 首先定义500个线程池
- `CountDownLatch`计数器初始值设为300,是 Java 并发工具类，中文叫 “倒计时门闩”,表示需要等待 300 个 “事件” 完成后，主线程才能继续执行。
- **`Runnable task = () -> {...}`**：用 Lambda 表达式创建一个 Runnable 任务（替代匿名内部类，简化代码），这个任务是每个线程要执行的逻辑。
- **`latch.countDown()`**：当前任务执行完毕，把 CountDownLatch 的计数器减 1（比如第 1 个任务执行完，计数器从 300 → 299；第 300 个任务执行完，计数器变为 0）。
- **`es.submit(task)`**：把定义好的 `task` 提交到线程池 `es`（你之前定义的 `Executors.newFixedThreadPool(500)`），线程池会分配线程执行这个任务。
- 相当于把Runnable封装进了线程当中运行

# 实现优惠券秒杀下单

每个店铺都可以发布优惠券，分为平价券和特价券。平价券可以任意购买，而特价券需要秒杀抢购

![image-20260303152550599](/images/黑马点评/image-20260303152550599.png)

表关系如下：

- tb_voucher:优惠券的基本信息，优惠金额，使用规则等
- tb_seckill_voucher:优惠券的库存、开始抢购时间，结束抢购时间。特价优惠券才需要填写这些信息

`@TableField `注解来自 MyBatis-Plus,用于定义实体类字段与数据库表列之间的映射关系。它提供了多种选项来控制字段在数据库操作中的行为。当设置 exist = false 时，告诉 MyBatis-Plus：该字段在数据库表中不存在MyBatis-Plus 在 SQL 操作（INSERT、UPDATE、SELECT、DELETE）时会忽略这个字段,该字段仅用于 Java 代码中的业务逻辑或数据传输。

## 功能

下单时需要判断2点：

- 秒杀是否开始或结束，如果尚未开始或已经结束则无法下单
- 库存是否充足，不足则无法下单

![image-20260303170232634](/images/黑马点评/image-20260303170232634.png)

```VoucherServiceImpl.java
    /**
     * 秒杀优惠券
     * @param voucherId
     * @return
     */
    @Override
    public Result seckillVoucher(Long voucherId) {
        // 1.查询优惠券
        SeckillVoucher voucher = seckillVoucherService.getById(voucherId);

        // 2.判断秒杀是否开始
        if (voucher.getBeginTime().isAfter(LocalDateTime.now())) {
            //尚未开始
            return Result.fail("秒杀尚未开始");
        }

        // 3.判断秒杀是否已经结束
        if (voucher.getEndTime().isBefore(LocalDateTime.now())) {
            //已经结束
            return Result.fail("秒杀已经结束");
        }

        // 4.判断库存是否充足
        if (voucher.getStock() < 1) {
            return Result.fail("库存不足");
        }

        // 5.扣减库存
        boolean success = seckillVoucherService.update()
                .setSql("stock = stock - 1")
                .eq("voucher_id", voucherId).update();//where voucher_id = ?
        if(!success){
            // 扣减失败
            return Result.fail("库存不足");
        }

        // 6.创建订单
        VoucherOrder voucherOrder = new VoucherOrder();
        // 6.1.订单id
        long orderId = redisIdWorker.nextId("order");
        voucherOrder.setId(orderId);
        // 6.2.用户id
        voucherOrder.setUserId(UserHolder.getUser().getId());
        // 6.3.代金券id
        voucherOrder.setVoucherId(voucherId);
        save(voucherOrder);
        // 7.返回订单ID


        return null;
    }
```

## 思想：

- 从秒杀优惠券数据库中根据id查询优惠券`seckillVoucherService.getById(voucherId)`
- 判断秒杀是否开始、秒杀是否已经结束、库存是否充足
- 通过mp语句进行sql查询`boolean success = seckillVoucherService.update().setSql("stock = stock - 1").eq("voucher_id", voucherId).update();`
  - `setSql`是update的语句，指代对什么进行修改，eq就好像where会返回一个boolean的值
- 创建订单
  - 其中订单id需要使用`redisIdWorker.nextId("order");`生成全局唯一ID

## 超卖问题是典型的多线程安全问题，针对这一问题的常见解决方案就是加锁：

### 悲观锁：

认为线程安全问题一定会发生，因此在操作数据之前先获取锁，确保线程串行执行

- 例如Synchronized、Lock都属于悲观锁

### 乐观锁：

认为线程安全问题不一定会发生，因此不加锁，只是在更新数据时去判断有没有其他线程对数据做了修改。

- 如果没有修改则认为是安全的，自己才更新数据
- 如果已经被其他线程修改说明发生了安全问题，此时可以重试或异常

乐观锁的关键是判断之前查询得到的数据是否有被修改过，常见的方式有2种：

- 版本号法
  - 通过判断版本号是否发生变化来进行加锁![image-20260304104556022](/images/黑马点评/image-20260304104556022.png)
- CAS法
  - ![image-20260304105813107](/images/黑马点评/image-20260304105813107.png)
  - ![image-20260304105803702](/images/黑马点评/image-20260304105803702.png)
  - 成功率太低

### 悲观锁和乐观锁的比较

- 悲观锁比乐观锁的性能低：悲观锁需要先加锁再操作，而乐观锁不需要加锁，所以乐观锁通常具有更好的性能。
- 悲观锁比乐观锁的冲突处理能力低：悲观锁在冲突发生时直接阻塞其他线程，乐观锁则是在提交阶段检查冲突并进行重试。
- 悲观锁比乐观锁的并发度低：悲观锁存在锁粒度较大的问题，可能会限制并发性能；而乐观锁可以实现较高的并发度。
- 应用场景：两者都是互斥锁，悲观锁适合写入操作较多、冲突频繁的场景；乐观锁适合读取操作较多、冲突较少的场景。
- 悲观锁：添加同步锁，让线程串行执行
  - 优点：简单粗暴
  - 缺点：性能一般
- 乐观锁：不加锁，在更新时判断是否有其它线程在修改
  - 优点：性能好
  - 缺点：存在成功率低的问题

## 使用悲观锁实现一人一单

```VoucherOrderServiceImpl.java
@Service
public class VoucherOrderServiceImpl extends ServiceImpl<VoucherOrderMapper, VoucherOrder> implements IVoucherOrderService {

    @Resource
    private ISeckillVoucherService seckillVoucherService;

    @Resource
    private RedisIdWorker redisIdWorker;

    /**
     * 秒杀优惠券
     *
     * @param voucherId
     * @return
     */
    @Override
    @Transactional
    public Result seckillVoucher(Long voucherId) {
        // 1.查询优惠券
        SeckillVoucher voucher = seckillVoucherService.getById(voucherId);

        // 2.判断秒杀是否开始
        if (voucher.getBeginTime().isAfter(LocalDateTime.now())) {
            //尚未开始
            return Result.fail("秒杀尚未开始");
        }

        // 3.判断秒杀是否已经结束
        if (voucher.getEndTime().isBefore(LocalDateTime.now())) {
            //已经结束
            return Result.fail("秒杀已经结束");
        }

        // 4.判断库存是否充足
        if (voucher.getStock() < 1) {
            return Result.fail("库存不足");
        }
        Long userId = UserHolder.getUser().getId();
        //intern将字符串对象加入字符串常量池（String Pool）并返回常量池中的引用,这样就避免了同一个用户创建新的对象，可以确保锁一样
        //toString里面底层就是new了一个String对象，所以每一次使用toString，这个对象都会变为新的对象，所以这里使用toString()方法
        synchronized (userId.toString().intern()) {
            //获取代码对象(事物)
            IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();
            return proxy.createVoucherOrder(voucherId);
        }
    }

    @Transactional
    public Result createVoucherOrder(Long voucherId) {
        // 6.一人一单
        Long userId = UserHolder.getUser().getId();

        // 6.1.查询订单
        Integer count = query().eq("user_id", userId).eq("voucher_id", voucherId).count();

        // 6.2.判断是否存在
        if (count > 0) {
            //用户已经购买过了
            return Result.fail("用户已经购买过一次了");
        }

        // 5.扣减库存
        boolean success = seckillVoucherService.update()
                .setSql("stock = stock - 1")//update set
                .eq("voucher_id", voucherId).gt("stock", 0)//where id = ? and stock > 0
                .update();
        if (!success) {
            // 扣减失败
            return Result.fail("库存不足");
        }
        // 7.创建订单
        VoucherOrder voucherOrder = new VoucherOrder();
        // 7.1.订单id
        long orderId = redisIdWorker.nextId("order");
        voucherOrder.setId(orderId);
        // 7.2.用户id
        voucherOrder.setUserId(UserHolder.getUser().getId());
        // 7.3.代金券id
        voucherOrder.setVoucherId(voucherId);
        save(voucherOrder);
        // 8.返回订单ID
        return Result.ok(orderId);
    }

}
```

## 思路

- 将原本的一人一单的代码开始到返回订单ID进行封装

- 通过UserHolder获取到当前用户的用户id

- 在通过`query().eq("user_id", userId).eq("voucher_id", voucherId).count();`查询订单

  - 如果订单存在则提示用户已经购买了

- 反之扣减库存，使用`seckillVoucherService.update()..setSql("stock = stock - 1")..eq("voucher_id", voucherId).gt("stock", 0).update();`使用update().setSQL()设置set的值，`eq()`函数进行where判定，`gt("stock", 0)`函数相当于`stock > 0`如果返回为假，则提示库存不足

- 创建订单之后返回订单ID

- ```VoucherOrderServiceImpl.java
  synchronized (userId.toString().intern()) {
      //获取代码对象(事物)
      IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();
      return proxy.createVoucherOrder(voucherId);
  }
  ```

  - 为什么这里要用`userId.toString()`

    - toString里面底层就是new了一个String对象，所以每一次使用toString，这个对象都会变为新的对象，所以这里使用toString()方法
  
  - 为什么要用`.intern()`
  
    -  intern将字符串对象加入字符串常量池（String Pool）并返回常量池中的引用,这样就**避免了同一个用户创建新的对象**，可以确保锁一样
  - `IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();`
    - `AopContext.currentProxy()`
      - `AopContext`Spring AOP 提供的工具类，作用是**保存当前线程的 AOP 代理对象**（ThreadLocal 存储），让开发者能在业务方法内部获取到代理对象。
      - **`currentProxy()`**：`AopContext` 的静态方法，核心作用是**获取当前线程中正在执行的目标对象的 AOP 代理对象**。
    - 这里调用的`IVoucherOrderService`中的代理，将上面的`createVoucherOrder`方法封装成一个接口，通过动态代理运行接口
    - **为什么用代理？** 因为 `createVoucherOrder` 上有 `@Transactional` 注解，直接调用 `this.createVoucherOrder()` 会导致事务失效（Spring AOP 代理机制）。通过 `AopContext.currentProxy()` 获取当前代理对象，再调用方法，可以确保事务生效。
  - `synchronized`
    - 当有多个线程访问同一个对象中的`synchronized`代码块的时候，同一时刻只有一个线程能执行，其他的线程会被阻塞，必须等当前线程执行完之后才能执行代码块。在执行synchronized代码块时会锁定当前的对象，**只有执行完该代码块才能释放该对象锁，下一个线程才能执行并锁定该对象**，一个对象就一个锁。
  
- `@EnableAspectJAutoProxy(exposeProxy = true)`这个必须放在启动类中，用于扫描AOP进行代理

## 不熟悉的点

synchronized可以**保证方法或者代码块在运行**时，同一时刻只有一个方法可以进入到临界区，同时它还可以保证共享变量的内存可见性，Java中每一个对象都可以作为锁，这是synchronized实现同步的基础。

修饰的对象有以下几种：

- 修饰一个**代码块**，被修饰的代码块称为同步语句块，其作用的范围是大括号{}括起来的代码，作用的对象是调用这个代码块的对象；

- 修饰一个**方法**，被修饰的方法称为同步方法，其作用的范围是整个方法，作用的对象是调用这个方法的对象；

- 修饰一个**静态的方法**，其作用的范围是整个静态方法，作用的对象是这个类的所有对象；

- 修饰一个**类**，其作用的范围是synchronized后面括号括起来的部分，作用主的对象是这个类的所有对象。

### synchronized的使用

- synchronized修饰代码块
  - 修饰一个代码块，被修饰的代码块称为同步语句块，其作用的范围是大括号{}括起来的代码，作用的对象是调用这个代码块的对象。
  - 多个线程访问 同一对象 的同步代码块
    - 一个线程访问一个对象中的synchronized(this)同步代码块时，其它线程试图访问该对象的线程将被阻塞。
    - 当两个并发线程(thread1和thread2)访问同一个对象（这个很重要）(ThreadSyn)中的synchronized代码块时，在同一时刻只能有一个线程得到执行，**另一个线程受阻塞**，必**须等待当前线程执行完这个代码块以后才能执行该代码块**。Thread1和thread2是互斥的，因为在执行synchronized代码块时会锁定当前的对象，**只有执行完该代码块才能释放该对象锁，下一个线程才能执行并锁定该对象**，一个对象就一个锁。

```ILock.java
public interface ILock {

    /**
     * 尝试获取锁
     * @param timeoutSec
     * @return
     */
    boolean tryLock(long timeoutSec);

    /**
     * 释放锁
     */
    void unLock();
}

```

```SimpleRedisLock.java
public class SimpleRedisLock implements ILock{

    private String name;
    private StringRedisTemplate stringRedisTemplate;

    public SimpleRedisLock(String name, StringRedisTemplate stringRedisTemplate) {
        this.name = name;
        this.stringRedisTemplate = stringRedisTemplate;
    }

    private static final String KEY_PREFIX = "lock:";

    @Override
    public boolean tryLock(long timeoutSec) {
        long threadId = Thread.currentThread().getId();
        Boolean success = stringRedisTemplate.opsForValue().setIfAbsent(KEY_PREFIX + name, threadId + "", timeoutSec, TimeUnit.SECONDS);
        return Boolean.TRUE.equals(success);
    }

    @Override
    public void unLock() {
        //释放锁
        stringRedisTemplate.delete(KEY_PREFIX + name);
    }
}
```

`ILock.java`和`SimpleRedisLock.java`并没有加入spring容器当中，如果想要在spring中使用，就需要new对象。

`SimpleRedisLock`通过接口`ILock`重写获取锁和释放锁，`Thread.currentThread().getId();`获取当前线程的id，也就是用户id。

`stringRedisTemplate.opsForValue().setIfAbsent(KEY_PREFIX + name, threadId + "", timeoutSec, TimeUnit.SECONDS);`对应Redis的`SET lock:order:123 "5678" EX 1200 NX`，setIfAbsent自带EX开启互斥锁，设置逾期时间为NX。返回值Boolean值需要拆箱，可以使用Boolea.True.equals()来进行判断返回真假。

用Redis锁的时候：

用户 A → 请求 1 → 服务器 1 (JVM1)
            → 请求 2 → 服务器 2 (JVM2)

- 服务器2上的请求完全不受影响，可以绕过锁

## 改进Redis的分布式锁—解决Redis分布式锁误删问题

改进的点：误删锁

需求：修改之前的分布式锁实现，满足：

1. 在获取锁时存入线程标示(可以用UUID表示)
2. 在释放锁时先获取锁中的线程标示，判断是否与当前线程标示一致
   1. 如果一致则释放锁
   2. 如果不一致则不释放锁

```SimpleRedisLock.java
public class SimpleRedisLock implements ILock{

    private String name;
    private StringRedisTemplate stringRedisTemplate;

    public SimpleRedisLock(String name, StringRedisTemplate stringRedisTemplate) {
        this.name = name;
        this.stringRedisTemplate = stringRedisTemplate;
    }

    private static final String KEY_PREFIX = "lock:";
    private static final String ID_PREFIX = UUID.randomUUID().toString(true) + "-";

    @Override
    public boolean tryLock(long timeoutSec) {
        String threadId =ID_PREFIX + Thread.currentThread().getId();
        Boolean success = stringRedisTemplate.opsForValue().setIfAbsent(KEY_PREFIX + name, threadId, timeoutSec, TimeUnit.SECONDS);
        return Boolean.TRUE.equals(success);
    }

    @Override
    public void unLock() {
        //获取线程标示
        String threadId =ID_PREFIX + Thread.currentThread().getId();

        //获取锁中的标示
        String id = stringRedisTemplate.opsForValue().get(KEY_PREFIX + name);

        //判断标示是否一致
        if (threadId.equals(id)) {
            //释放锁
            stringRedisTemplate.delete(KEY_PREFIX + name);
        }

    }
}
```

### 思路

- 对于锁id我们进行更改，通过`UUID.randomUUID().toString(true) + "-"`来确保唯一性，由于UUID的特性导致线程id出现重复的概率极低，然后拼接`ID_PREFIX`和线程id实现值得唯一性。
- 缓存得线程值需要进行判断
  - 通过key获取对应得缓存值
  - 判断是否和原本你的线程值是否相同
    - 标示一致释放锁。
    - 不一致就结束

## 分布式锁的原子性问题

JVM有**垃圾回收机制**，当线程1要释放锁的时候可能会出现阻塞，一旦发生阻塞且足够长，就容易触发超时释放，然而线程2这个时候来获取锁，因为已经超时释放了锁，所以就会重新获取锁，就在阻塞结束去释放锁的动作**(在判断后阻塞的)**就会把线程2获取的锁给释放掉。

## JAVA调用Lua脚本改造分布式锁

需求：基于Lua脚本实现分布式锁的释放锁逻辑

提示：RedisTemplate调用Lua脚本的API如下

```unlock.lua
-- 比较线程标示与锁中的标示是否一致
if(redis.call('get',KEYS[1]) == ARGV[1]) then
    -- 释放锁 del key
    return redis.call('del',KEYS[1])
end
-- 不一致，则直接返回
return 0
```

使用Lua脚本将判断锁标示和删除锁两个操作合并成一个原子操作(即同时操作)

```SimpleRedisLock.java
    private static final DefaultRedisScript<Long> UNLOCK_SCRIPT;
    static{
        UNLOCK_SCRIPT = new DefaultRedisScript<>();
        UNLOCK_SCRIPT.setLocation(new ClassPathResource("unlock.lua"));
        UNLOCK_SCRIPT.setResultType(Long.class);
    }
    public void unLock() {
        //调用Lua脚本
        stringRedisTemplate.execute(
                UNLOCK_SCRIPT,
                Collections.singletonList(KEY_PREFIX + name),
                ID_PREFIX + Thread.currentThread().getId()
                );
    }
```

由于`RedisScript`是接口类并不能实例化，而`DefaultRedisScript`是实现类可以实例化，使用static静态代码块的原因是为了在使用了一次`SimpleRedisLock`类之后使用了一次static静态代码块之后，类首次加载之后，后续所有实例天然拥有，全员共享。在`DefaultRedisScript`中有一个`setLocation`函数，可以新建一个`ClassPathResource`对象来识别`unlock.lua`并且使用`setResultType`规定结果类型设置为Long型

修改unLock方法：

- 使用`stringRedisTemplate.execute()`来调用Lua脚本

- `Collections.singletonList(KEY_PREFIX + name)`:这行代码创建一个不可变的、只包含一个元素的 List

- ```JAVA
  // 传统写法（更啰嗦）
  List<String> keys = new ArrayList<>();
  keys.add("lock:order:123");
  // 但这个 List 可以被修改（添加/删除元素）
  
  // singletonList 写法（更简洁）
  List<String> keys = Collections.singletonList("lock:order:123");
  // 这个 List 不能被修改，只能读
  ```

这样修改unLock方法之后就可以通过调用`unlock.lua`解决判断锁标示和释放锁同时发生的原子性问题

实现思路：

- 利用set nx ex获取锁，并设置过期时间，保存线程标示
- 释放锁时先判断线程标示是否与自己一致，一致则删除锁

特性：

- 利用set nx满足互斥性
- 利用set nx保证故障时锁依然能释放，避免死锁，提高安全性
- 利用Redis集群保证高可用和高并发特性

## Redisson功能介绍

基于setnx实现的分布式锁存在下面的问题：

1. 不可重入
   1. 同一个线程无法多次获取同一把锁
2. 不可重试
   1. 获取锁只尝试一次就返回false，没有重试机制
3. 超时释放
   1. 锁超时释放虽然可以避免死锁，但如果业务执行耗时较长，也会导致锁释放，存在安全隐患
4. 主从一致性
   1. 如果redis提供了主(写)从(读)集群，主从同步存在延迟，当主宕机时，如果从并同步主中的锁数据，则会出现锁实现

Redisson是一个在Redis的基础上实现的JAVA驻内存数据网络(In-Memory Data Grid)。它不仅提供了一系列的分布式的Java常用对象，还提供了许多分布式服务，其中就包含了各种分布式锁的实现。

**关键优势**：

1. **降低开发成本**：无需手写 Lua 脚本或处理底层命令，直接调用 JUC 标准接口，提升开发效率 。

2. **生产级可靠**：内置容错、重试、锁续期、连接池管理，适配高并发与分布式环境 。

3. **生态完善**：无缝集成 Spring Boot、Spring Cache、Hibernate、Quarkus 等框架，支持 JCache 标准Redisson。

4. **跨平台兼容**：支持 Redis/Valkey 全系列部署形态，云厂商托管服务即接即用Redisson。

8. 分布式锁(Lock)和同步器(Synchronizer)

   2. 公平锁(Fair Lock)
   3. 联锁(MultiLock)
   4. 红锁(RedLock)
   5. 读写锁(ReadWriteLock)

## Redisson的可重入锁原理

![image-20260309145053810](/images/黑马点评/image-20260309145053810.png)

如果获取锁成功之后进入method2之后又执行了一次尝试获取锁操作，这就是可重入锁。但是这里由于第一个tryLock已经获取到锁了，因为nx的特性，所以第二次tryLock并不能获取锁。

![Screenshot_2026-03-09-16-00-19-085_tv.danmaku.bil](/images/黑马点评/Screenshot_2026-03-09-16-00-19-085_tv.danmaku.bil.jpg)

### 思路

- 通过每一次尝试获取锁就对hash得值进行+1并且重置锁得有效期时间
- 反之如果需要释放锁就对value得值-1并且判断value是否为0，如果为0则释放锁--->这里就需要原子性问题，使用Lua脚本实现

```trylock.lua
local key = KEYS[1]; --锁得key
local threadId = ARGV[1]; --线程唯一标识
local releaseTime = ARGV[2]; --锁的自动释放时间
-- 判断是否存在
if(redis.call('exists',key) == 0) then
	-- 不存在，获取锁
	redis.call('hset',key,threadId,'1');
	-- 设置有效期
	redis.call('expire',key,releaseTime);
	return 1; --返回结果
end
-- 锁已经存在，判断threadId是否是自己
if(redis,call('hexists',key,threadId) == 1) then
	-- 不存在，获取锁，重入次数+1
	redis.call('hincrby',key,threadId,'1');
	-- 设置有效期
	redis.call('expire',key,releaseTime);
	return 1; -- 返回结果
end
return 0;
```

以上是获取锁的lua脚本

- 首先判断key是否存在，如果不存在就使用hset方式设置key并且value初始化为1并且设置有效期时间
- 如果锁存在，就判断threadId是否是自己的
  - 如果不存在就获取锁并且初始化为1，并且设置有效期时间

```unlock.lua
local key = KEYS[1]; --锁得key
local threadId = ARGV[1]; --线程唯一标识
local releaseTime = ARGV[2]; --锁的自动释放时间
-- 判断当前锁是否还是被自己所持有
if(redis.call('HEXISTS',key,threadId) == 0) then
	return nil;-- 如果已经不是自己，则直接返回
end;
-- 是自己的锁，则重入次数-1
local count = redis.call('hincrby',key,threadId,-1);
-- 判断是否重入次数是否已经为0
if (count > 0) then
	-- 大于0说明不能释放锁，重置有效期然后返回
	redis.call('EXPIRE',key,releaseTime);
	return nil;
else -- 等于0说明可以释放锁，直接删除
	redis.call('DEL',key);
	return nil;
end
```

以上是释放锁的lua脚本

- 加入method1进入到了method2之后再次获取锁之前判断这个锁是否被自己锁持有
  - 如果不是自己的直接返回
  - 是自己的锁则重入次数-1
- 判断重入次数是否为0
  - 如果重入次数大于0说明不能释放锁，重置有效期然后返回
  - 如果重入次数等于0则直接释放锁

## Redisson的multiLock原理

### Redisson分布式锁主从一致性问题

![image-20260310160331701](/images/黑马点评/image-20260310160331701.png)

这里Redisson 分布式锁在 Redis 主从架构下的 “主从一致性问题”，本质是**主从异步复制**导致的锁数据丢失风险。

当Java应用尝试向redis master获取锁的时候，主从同步延迟，在同步完成前，Redis Master突然宕机了(**导致数据没有同步**)，这时master的数据**没有及时的同步到slave**上，Redis 集群进行故障转移，Slave 被提升为新的 Master。

由于新的master并没有该锁，所以当另一个线程来请求锁的时候，**锁失效**，因此就需要重新加锁。

最终结果：**thread1 和 thread2 同时持有同一把锁**，分布式锁的 “互斥性” 被破坏，引发并发安全问题（比如超卖、数据错乱）。

![image-20260310162016218](/images/黑马点评/image-20260310162016218.png)

我们采用**红锁**来解决"主从异步复制导致锁失效"的问题，不再依赖单个 Redis 主从集群，而是用**多个独立的 Redis 节点（每个节点自己也是主从架构）**，通过 “多数派共识” 来保证分布式锁的安全性。

- 步骤：Java 应用向多个 Redis Node 并发请求加锁
  - 命令：`SET lock thread1 NX EX 10`（和之前一样，保证互斥 + 自动过期）
  - 目标：向 **3 个独立的 Redis Node** 同时发起加锁请求（图里是 3 个，实际可以是 5/7 等奇数个节点）
  - 每个 Node 都是独立的：它们之间**没有主从关系**，各自维护自己的锁数据，互不影响。
- 核心判断：是否满足 “多数派加锁成功”
  - RedLock 算法要求：
    - 加锁成功的节点数 **> 总节点数的一半**（比如 3 个节点，至少 2 个成功）
    - 且整个加锁过程的耗时 **小于锁的过期时间**（比如 10 秒）
  - 现在的方案：
    - 锁存在 **多个独立节点** 上，即使其中 1 个节点宕机，只要剩下的节点里还有超过半数保存了锁数据，锁依然有效。
    - 比如 3 个节点，最多允许 1 个节点宕机，剩下 2 个节点依然能保证锁的存在，不会出现 “锁丢失” 的情况。

源码：

```RedissonMultiLock.class

        long newLeaseTime = -1L;
        if (leaseTime != -1L) {
            if (waitTime == -1L) {
                newLeaseTime = unit.toMillis(leaseTime);
            } else {
                newLeaseTime = unit.toMillis(waitTime) * 2L;
            }
        }

        long time = System.currentTimeMillis();
        long remainTime = -1L;
        if (waitTime != -1L) {
            remainTime = unit.toMillis(waitTime);

```

`leaseTime`：**锁的持有时间**（自动释放时间），`-1` 表示 “不自动释放，由看门狗续期”。

`waitTime`：**获取锁的最大等待时间**，`-1` 表示 “一直等待直到获取锁”。

`unit`：时间单位（比如 `TimeUnit.SECONDS`），用来把 `leaseTime`/`waitTime` 转成毫秒。

`newLeaseTime`：最终计算出的**实际锁自动释放时间（毫秒）**，初始值 `-1` 代表 “未设置”。

场景1：只指定 `leaseTime`，不指定 `waitTime`

- `lock.tryLock(-1, 30, TimeUnit.SECONDS);`

  - `leaseTime = 30，waitTime = -1`
  - 计算：`newLeaseTime = 30秒 → 30000毫秒`
  - 含义：**锁最多持有 30 秒后自动释放**，获取锁时会一直等待直到成功。

场景2：同时指定 `waitTime` 和 `leaseTime`

- `lock.tryLock(10, 30, TimeUnit.SECONDS);`
  - `leaseTime = 30，waitTime = 10`
  - 计算：`newLeaseTime = 10秒 * 2 → 20000毫秒`
  - 含义：**锁的自动释放时间是等待时间的 2 倍**（这里是 20 秒），避免 “**锁还没获取到就已经过期**” 的问题。

场景3：不指定 `leaseTime（leaseTime = -1`）

- `lock.tryLock(10, -1, TimeUnit.SECONDS);`
  - `leaseTime = -1`，外层 `if` 不执行
  - `newLeaseTime` 保持 -1
  - 含义：**锁不会自动释放**，Redisson 会启动看门狗（Watchdog），每 10 秒续期一次，直到手动解锁。

### 总结

1. 不可重入Redis分布式锁：
   - 原理：利用setnx的互斥性；利用ex避免死锁；释放锁时判断线程标示
   - 缺陷：不可重入、无法重试、锁超时失效
2. 可重入的Redis分布式锁
   - 原来：利用hash结构，记录线程标示和重入次数；利用watchDog延续锁时间；利用信号量控制锁重试等待
   - 缺陷：redis宕机引起锁失效问题
3. Redisson的multiLock
   - 原理：多个独立的Redis节点，必须再所有节点都获取重入锁，才算获取锁成功
   - 缺陷：运维成本高、实现复杂

## 思想

我们根据前面的思想，我们下单流程是用户通过前端的nginx提交数据，然后给到tomcat判断(查询优惠券->判断秒杀库存->查询订单->校验一人一单->减库存->创建订单)最后进行数据交互。但是这样的流程，需要花费很多时间，比如餐馆服务员问用户需要点什么，然后记录，再然后给后厨说并且等着，后厨做好之后又给服务员，服务员再给用户。这一系列得流程可以优化成如上图所示，分成2个线程来执行(就好像服务员把单子给到后厨就去给用户订单号，后厨做饭一样，这里就把查询优惠券到一人一单得判断分为一部分，异步一个减库存和创建订单得过程)，使用redis把判断秒杀库存和校验一人一单提取出来，就如上图所示了。

由于订单一般是不能重复的，所以这里使用的set结构的redis数据管理，为什么要使用set来管理呢？

核心目的是解决两个高并发问题

- 防止**同一个用户重复下单 / 领券**（幂等性控制）
  - 优势
    - Redis 集合操作是**原子性**的，高并发下不会出现 “判断和插入不是一步” 的竞态条件。
    - 查找用户是否存在的时间复杂度是 O (1)，性能极高，适合秒杀场景。
- 保证**库存扣减和用户限购的原子性**（Lua 脚本）
  - 整个判断逻辑（库存是否充足 + 用户是否已下单）是放在 **Lua 脚本** 里执行的。
  - Lua 脚本在 Redis 中是**原子执行**的：
    - 不会被其他请求打断，避免 “超卖” 和 “重复下单”。
    - 先查库存 → 再查用户是否已下单 → 最后扣库存 + 记录用户，这三步是一个不可分割的原子操作。

                Collections.emptyList(),
                voucherId.toString(),
                userId.toString()
        );
        // 2.判断结果是否为0
        int r = result.intValue();
        if (r != 0) {
            // 2.1.不为0，代表没有购买资格
            return Result.fail(r == 1 ? "库存不足" : "不能重复下单");

        }
        // 2.2.为0，有购买资格，把下单信息保存到阻塞队列
        // 2.3创建订单
        VoucherOrder voucherOrder = new VoucherOrder();
        // 2.4.订单id
        long orderId = redisIdWorker.nextId("order");
        voucherOrder.setId(orderId);
        // 2.5.用户id
        voucherOrder.setUserId(UserHolder.getUser().getId());
        // 2.6.代金券id
        voucherOrder.setVoucherId(voucherId);
        // 2.6.放入阻塞队列
        orderTasks.add(voucherOrder);

        // 3.获取代理对象
        proxy = (IVoucherOrderService) AopContext.currentProxy();

        // 4.返回订单id
        return Result.ok(orderId);

    }
        @Transactional
    public void createVoucherOrder(VoucherOrder voucherOrder) {
        // 5.一人一单
        // 5.1.查询订单
        Integer count = query().eq("user_id", voucherOrder.getUserId()).eq("voucher_id", voucherOrder).count();
        // 5.2.判断是否存在
        if (count > 0) {
            //用户已经购买过了
            log.error("用户已经购买过了");
            return;
        }

        // 6.扣减库存
        boolean success = seckillVoucherService.update()
                .setSql("stock = stock - 1")//update set
                .eq("voucher_id", voucherOrder.getVoucherId()).gt("stock", 0)//where id = ? and stock > 0
                .update();
        if (!success) {
            // 扣减失败
            log.info("库存不足");
            return;
        }
        // 7.创建订单
        save(voucherOrder);
    }
```

##### 思路梳理

按照前面的思路

lua脚本返回为0的时候，说明用户有购买资格，需要把下单信息保存到阻塞队列当中。因此我们需要创建一个阻塞队列`private BlockingQueue<VoucherOrder> orderTasks = new ArrayBlockingQueue<>(1024 * 1024);`为什么我们要创建一个数组类型的阻塞队列呢？由于秒杀场景的特点是：

- 瞬间涌入大量请求（突发性）
- 需要快速响应，不能无限等待
- 必须保护系统不崩溃

而`ArrayBlockingQueue`类型紧凑、缓存命中率高、内存可控，使用场景为：突发流量、有界缓冲，`ArrayBlockingQueue` 是**有界队列**，能防止请求无限制堆积导致 OOM，非常适合秒杀场景；如果用无界队列，极端情况下会把内存打满。数组的优势：

ArrayBlockingQueue 内存布局：
┌─────────────────────────────────┐
│ [订单1][订单2][订单3]...[订单N] │ ← 连续内存空间
└─────────────────────────────────┘
       ↑           ↑
     head     tail

由于我们需要时刻能够从阻塞队列中把订单信息获取出来，所以我们需要不断地监听运行时的状态，因此通过内部类调用接口`Runnable`的run方法在运行时一直监听阻塞队列中的任务，获取队列中的订单信息。

# Redis消息队列实现异步秒杀

**消息队列(Message Queue)**，字面意思就是存放消息的队列。最简单的消息队列模型包括3个角色：

- 消息队列：存储和管理消息，也被称为消息代理(Message Broker)
- 生存者：发送消息到消息队列
- 消费者：从消息队列获取消息并处理消息

![image-20260314135203617](/images/黑马点评/image-20260314135203617.png)

Redis提供了三种不同得方式来实现消息队列：

- list结构：基于List结构模拟消息队列
- PubSub：基本得点对点消息模型
- Stream：比较完善得消息队列模型

## 基于List结构模拟消息队列

消息队列(Message Queue)，字面意思就是存放消息的队列。而Redis的list数据结构是一个双向链表，很容易模拟出队列效果。

队列是入口和出口不在一边，因此我们可以利用：LPUSH结合RPOP、或者RPUSH结合LPOP来实现。

不过要注意的是，当队列中没有消息时RPOP或LPOP操作会返回null，并不像JVM的阻塞队列那样会阻塞并等待消息。因此这里应该使用BRPOP或者BLPOP来实现阻塞效果。

![image-20260314143818495](/images/黑马点评/image-20260314143818495.png)

### 有哪些优缺点？

优点：

- 利用Redis存储，不受限于JVM内存上限
- 基于Redis的持久化机制，数据安全性有保证
- 可以满足消息有序性

缺点：

- 无法避免消息丢失
- 只支持单消费者

## 基于PubSub的消息队列

**PubSub(发布订阅)**是Redis2.0版本引入的消息传递模型。顾名思义，消费者可以订阅一个或多个channel，生产者向对应channel发送消息后，**所有订阅者都能收到相关消息。**

- SUBSCRIBE channel [channel]：订阅一个或多个频道
- PUBLISH channel msg：向一个频道发送消息
- PSUBSCRIBE pattern [pattern]：订阅与**pattern格式匹配的所有频道**

![image-20260314150205520](/images/黑马点评/image-20260314150205520.png)

![image-20260314150339430](/images/黑马点评/image-20260314150339430.png)

一个使用subscribe，一个使用psubscribe命令，由于psubscribe可以设置pattern格式匹配，所以只要是order.*的数据都可以接受如上图所示，这样就实现了既可以给单一的消费者发送消息同时也可以给多个消费者发送消息。

### 优缺点

优点：

- 采用发布订阅模型，支持多生产、多消费

缺点：

- 不支持数据持久化
- 无法避免消息丢失
- **消息堆积有上限**，**超出时数据丢失**

## 基于Stream的消息队列

Stream是Redis 5.0引入的一种新数据类型，可以实现一个功能非常完善的消息队列。

### XADD命令

`XADD key [NOMKSTREAM] [MAXLEN|MINID [=|~] threshold [LIMIT count]] *|ID field value [field value ...]`

- `NOMKSTREAM`:如果队列不存在，是否自动创建队列，默认是自动创建
- `[MAXLEN|MINID [=|~] threshold [LIMIT count]]`:设置消息队列的最大消息数量
- `*|ID`:消息的唯一id，*代表由Redis自动生成。格式是“**时间戳-递增数字**”，例如“1644804662707-0”
- `field value [field value ...]`:发送到队列中的消息，称为Entry。格式就是多个key-value键值对

例如：

```Redis
## 创建名为 users 的队列，并向其中发送一个消息，内容是：{name=jack,age=21}，并且使用Redis自动生成ID
XADD users * name jack age 21
```

### 读取消息的方式之一：XREAD

`XREAD [COUNT count] [BLOCK milliseconds] STREAMS key [key ...] ID [ID...]`

- `[COUNT count]`:每次读取消息的最大数量
- `[BLOCK milliseconds]`:当没有消息时，是否阻塞、阻塞时长
- `STREAMS key [key ...]`:要从那个队列读取消息，key就是队列名
- `ID [ID...]`:起始id，只返回大于该ID的消息
  - 0：代表从第一个消息开始
  - $：代表从最新的消息开始

![image-20260314154220483](/images/黑马点评/image-20260314154220483.png)

一旦添加之后，随时都可以查看当前的消息，但是如果想要查看最新的消息，就看不到已经查看的消息了，就比如邮箱一样。

XREAD阻塞读取的话，读取最新的消息：

![image-20260314155935635](/images/黑马点评/image-20260314155935635.png)

在业务开发中，我们可以**循环的调用XREAD阻塞方式来查询最新消息**，从而**实现持续监听队列得效果**，伪代码如下：

```伪代码
while(true){
	//尝试读取队列中得消息，最多阻塞2秒
	Object msg = redis.execute("XREAD COUNT 1 BLOCK 2000 STREAMS users $");
	if(msg == null){
		continue;
	}
	//处理消息
	handleMessage(msg);
}
```

注意：

当我们指定起始ID为$时，代表读取最新得消息，如果我们**处理一条消息得过程中，又有超过1条以上得消息到达队列**，则**下次获取时也只能获取到最新得一条**，会出现漏读消息得问题。

### STREAM类型消息队列的XREAD命令特点：

- 消息可回溯
- 一个消息可以被多个消费者读取
- 可以阻塞读取
- 有消息漏读的风险

## 基于Stream的消息队列-消费者组

**消费者组(Consumer Group)**:将多个消费者划分到一个组中，监听同一个队列。具备下列特点：

1. 消息分流
   - 队列中的消息会**分流给组内的不同消费者**，**而不是重复消费**，从而加快消息处理的速度
2. 消息标示
   - 消费者组会维护一个标示，记录最后一个被处理的消息，哪怕消费者宕机重启，还会从标示之后读取消息。确保每一个消息都会被消费。
3. 消息确认
   - 消费者获取消息后，消息处于pending状态，并存入一个pending-list。当处理完成后需要通过XACK来确认消息，标记消息为已处理，才会从pending-list移除

### 创建消费者组：

`XGROUP CREATE key groupName ID [MKSTREAM]`

- `key`:队列名称
- `groupName`：消费者组名称
- `ID`：起始ID标示，$代表队列中最后一个消息，0则代表队列中第一个消息
- `MKSTREAM`：队列不存在时自动创建队列

其他常见的命令：

删除指定的消费者组

- `XGROUP DESTORY key groupName`

给指定的消费者组添加消费者

- `XGROUP CREATECONSUMER key groupname consumername`

删除消费者组中的指定消费者

- `XGROUP DELCONSUMER key groupname consumername`

从消费者组读取消息

- `XREDGROUP GROUP group consumer [COUNT count] [BLOCK milliseconds] [NOACK] STREAMS key [key...] ID [ID...]`

  - `group`:消费者组名称
  - `consumer`:消费者名称，如果消费者不存在，会自动创建一个消费者
  - `count`:本次查询的最大数量
  - `BLOCK milliseconds`:当没有消息时最长等待时间
  - `NOACK`:无需手动ACK，获取到消息后自动确认
  - `STREAMS key`:指定队列名称
  - `ID`:获取消息的起始ID：
    - ">":从下一个未消费的消息开始
    - 其他：根据指定id从pending-list中获取已消费但未确认的消息，例如0，是从pending-list中的第一个消息开始

  ![image-20260316142819777](/images/黑马点评/image-20260316142819777.png)

确认消息

`XACK key group ID [ID...]`![image-20260316144337798](/images/黑马点评/image-20260316144337798.png)

读取pending-list中的数据

`XPENDING key group [[IDLE min-idle-time] start end count [consumer]]`

消费者监听消息的基本思路：

```伪代码
while(true){
	//尝试监听队列，使用阻塞模式，最长等待2000毫秒
	Object msg = redis.call("XREADGROUP GROUP g1 c1 COUNT 1 BLOCK 2000 STREAMS s1 >");
	if(msg == null){// null 说明没有消息，继续下一次
		continue;
	}
	try{
		//处理消息，完成后一定要ACK
		handleMessage(msg);
	}catch(Exception e){
		while(true){
			Object msg = redis.call("XREADGROUP GROUP g1 c1 COUNT 1 STREAMS s1 0");
			if(msg == null){// null 说明没有异常信息，所有消息都已确认，结束循环
				break;
			}
			try{
				//说明有异常消息，再次处理
				handleMessage(msg);
			}catch(Exception e){
				//再次出现异常，记录日志，继续循环
				continue;
			}
		}
	}
}
```

STREAM类型消息队列的XREADGROUP命令特点：

- 可以多消费者争论消息，加快消费速度
- 可以阻塞读取
- 没有消息漏读的风险
- 有消息确认机制，保证消息至少被消费一次

### 基于Redis的Stream结构作为消息队列，实现异步秒杀下单

需求：

1. 创建一个Stream类型的消息队列，名为stream.orders
2. 修改之前的秒杀下单Lua脚本，在认定有抢购资格后，直接向stream.orders中添加消息，内容包含voucherId、userId、orderId
3. 项目启动时，开启一个线程任务，尝试获取stream.orders中的消息，完成下单

-- 1.2.用户id
local userId = ARGV[2]
-- 1.3.订单id
local orderId = ARGV[3]

-- 2.数据key
-- 2.1.库存key，..是+

-- 2.2.订单key
local orderkKey = 'seckill:order:' .. voucherId

-- 3.脚本业务
-- 3.1.判断库存是否充足 get stockKey

if (stock == nil or stock <= 0) then
    -- 3.2.库存不足，返回 1

end

-- 3.2.判断用户是否下单 sismember orderKey userId

```VoucherOrderServiceImpl.java
private class VoucherOrderHandler implements Runnable {

        String queueName = "stream.orders";
        @Override
        public void run() {
            while (true) {
                try {
                    // 1.获取消息队列中的订单信息  XREADGROUP GROUP g1 c1 COUNT 1 BLOCK 2000 STREAMS stream.orders >
                    List<MapRecord<String, Object, Object>> list = stringRedisTemplate.opsForStream().read(
                            Consumer.from("g1", "c1"),
                            StreamReadOptions.empty().count(1).block(Duration.ofSeconds(2)),
                            StreamOffset.create(queueName, ReadOffset.lastConsumed())
                    );

                    // 2.判断消息获取是否成功
                    if (list == null || list.isEmpty()){
                        // 2.1.如果获取失败，说明没有消息，继续下一次循环
                        continue;
                    }
                    // 3.解析消息中的订单信息
                    MapRecord<String, Object, Object> record = list.get(0);
                    Map<Object, Object> values = record.getValue();
                    VoucherOrder voucherOrder = BeanUtil.fillBeanWithMap(values, new VoucherOrder(), true);
                    // 4.如果获取成功，可以下单
                    handleVoucherOrder(voucherOrder);

                    // 5.ACK确认,SACK stream.orders g1 id
                    stringRedisTemplate.opsForStream().acknowledge(queueName,"g1",record.getId());
                } catch (Exception e) {
                    log.error("处理订单异常", e);
                    handlePendingList();
                }

            }
        }

        private void handlePendingList() {
            while (true) {
                try {
                    // 1.获取pending-list中的订单信息  XREADGROUP GROUP g1 c1 COUNT 1 STREAMS stream.orders 0
                    List<MapRecord<String, Object, Object>> list = stringRedisTemplate.opsForStream().read(
                            Consumer.from("g1", "c1"),
                            StreamReadOptions.empty().count(1),
                            StreamOffset.create(queueName, ReadOffset.from("0"))
                    );

                    // 2.判断消息获取是否成功
                    if (list == null || list.isEmpty()){
                        // 2.1.如果获取失败，说明pending-list没有异常消息，结束下一次循环
                        break;
                    }
                    // 3.解析消息中的订单信息
                    MapRecord<String, Object, Object> record = list.get(0);
                    Map<Object, Object> values = record.getValue();
                    VoucherOrder voucherOrder = BeanUtil.fillBeanWithMap(values, new VoucherOrder(), true);
                    // 4.如果获取成功，可以下单
                    handleVoucherOrder(voucherOrder);

                    // 5.ACK确认,SACK stream.orders g1 id
                    stringRedisTemplate.opsForStream().acknowledge(queueName,"g1",record.getId());
                } catch (Exception e) {
                    log.error("处理pending-list订单异常", e);
                    try {
                        Thread.sleep(20);
                    } catch (InterruptedException ex) {
                        throw new RuntimeException(ex);
                    }
                }

            }
        }
    }

由于使用了Sream结构的消息队列，`xadd`会将消息放到队列当中，因此这时不在需要使用阻塞简化了流程，因此现在在spring初始化的时候，只需要把`VoucherOrderHandler`类加载就可以了。

由于lua脚本增加了一个元素以及使用了xadd创建名为 stream.orders 的队列，因此我们需要使用`XREADGROUP`来读取数据，就需要使用
`List<MapRecord<String, Object, Object>> list = stringRedisTemplate.opsForStream().read(Consumer.from("g1", "c1"),StreamReadOptions.empty().count(1).block(Duration.ofSeconds(2)),StreamOffset.create(queueName, ReadOffset.lastConsumed()));`对应命令:`XREADGROUP GROUP g1 c1 COUNT 1 BLOCK 2000 STREAMS stream.orders >`

关键参数解释：

- `Consumer.from("g1", "c1")`：指定消费者组名称为 g1，消费者名称为 c1
- `count(1)`：每次只读取 1 条消息（避免一次处理太多）
- `block(Duration.ofSeconds(2))`：阻塞等待最多 2 秒，如果没有新消息就返回空
- `ReadOffset.lastConsumed()`：从上次消费的位置继续读取（不会重复消费）

为什么拥塞时间设置不直接设置2000而是`Duration.ofSeconds(2)`？

1. 代码可读性更强
2. 类型安全
   - Duration.ofSeconds(2) 返回的是 Duration 对象，编译时就能检查类型
   - 如果方法需要 long 类型的毫秒值，直接写 2000 可能导致混淆

思路：

1. 读取消息
2. 判断是否获取到消息
3. 解析订单信息
4. 处理订单
5. ACK确认(不可或缺，如果不去ACK确认，pending-list会一直存在)
