FollowServiceImpl

```java
   	/**
     * 关注或取关
     * @param followUserId
     * @param isFollow
     * @return
     */
    @Override
    public Result follow(Long followUserId, Boolean isFollow) {
        // 1.获取登录用户
        Long userId = UserHolder.getUser().getId();

        // 2.判断到底是关注还是取关
        if (isFollow) {
            // 3.关注，新增数据
            Follow follow = new Follow();
            follow.setUserId(userId);
            follow.setFollowUserId(followUserId);
            save(follow);
        }else {
            // 4.取关，删除数据
            remove(new QueryWrapper<Follow>()
                    .eq("user_id", userId)
                    .eq("follow_user_id", followUserId));

        }
        return Result.ok();
    }

    /**
     * 判断是否关注
     * @param followUserId
     * @return
     */
    @Override
    public Result isFollow(Long followUserId) {
        // 1.获取登录用户
        Long userId = UserHolder.getUser().getId();
        // 2.查询是否关注
        Integer count = query().eq("user_id", userId).eq("follow_user_id", followUserId).count();
        // 3.返回结果
        return Result.ok(count > 0);
    }
```

`remove(new QueryWrapper<Follow>().eq("user_id", userId).eq("follow_user_id", followUserId));`这里对应的是`delete from tb_follow where user_id=? and follow_user_id = ?`

/**
 * 共同关注
 * @param id
 * @return
 */
@Override
public Result followCommons(Long id) {
    // 1.获取当前用户
    Long userId = UserHolder.getUser().getId();
    String key = "follows:" + userId;
    // 2.求交集
    String key2 = "follows:" + id;
    Set<String> intersect = stringRedisTemplate.opsForSet().intersect(key, key2);
    if (intersect == null || intersect.isEmpty()){
        // 无交集
        return Result.ok(Collections.emptyList());
    }
    // 3.解析id集合
    List<Long> ids = intersect.stream().map(Long::valueOf).collect(Collectors.toList());
    // 4.查询用户
    List<UserDTO> users = userService.listByIds(ids)
            .stream()
            .map(user -> BeanUtil.copyProperties(user, UserDTO.class))
            .collect(Collectors.toList());
    return Result.ok(users);
}
```

通过求2个key的交集实现共同关注，由于返回值是Set类型，因此需要解析id集合存储，最后根据交集出来的id查询用户信息(绰号和头像)

# 关注推送

关注推送也叫做Feed流，直译为投喂。为用户持续的提供“沉浸式”的体验，通过无限下拉刷新获取新的信息

![image-20260319141804366](/images/黑马点评/image-20260319141804366.png)

## Feed流的模式

Feed流产品有两种常见模式：

- TimeLine：不做内容筛选，简单的按照内容发布时间排序，常用于好友或关注。例如朋友圈
  - 优点：信息全面，不会有缺失。并且实现也相对简单
  - 缺点：信息噪音较多，用户不一定感兴趣，内容获取效率低
- 智能排序：利用智能算法屏蔽掉违规的、用户不感兴趣的内容。推送用户感兴趣信息来吸引用户
  - 优点：投喂用户感兴趣信息，用户粘度很高，容易沉迷
  - 缺点：如果算法不精准，可能起到反作用

本例中的个人页面，是基于关注的好友来做Feed流，因此采用Timeline的模式。该模式的实现方案有三种：

1. 拉模式
2. 推模式
3. 推拉结合

## Feed流的实现方案1

**拉模式**：也叫做读扩散

![image-20260319143320054](/images/黑马点评/image-20260319143320054.png)

博主发内容存在自己的**发件箱**，用户刷 Feed 时，再去拉取所有关注博主的发件箱，合并排序后展示。

1. **读放大问题严重**

- 当用户刷新 Feed 时，需要遍历**所有关注博主的发件箱**，拉取他们的最新内容。
- 如果用户关注了几百个博主，一次刷新就会产生几百次数据库查询，**读请求量会被急剧放大**，对数据库和缓存压力极大。
- 活跃用户越多，这种读放大效应越明显，容易成为系统瓶颈。

2. **延迟与性能问题**

- 每次刷新都要实时拉取、合并、排序多份数据，**响应时间会变长**，用户体验变差。
- 大 V 用户的发件箱会被大量粉丝频繁拉取，容易成为热点，导致**单点性能压力**，甚至引发缓存击穿 / 雪崩。

 3. **实现复杂度高**

- 需要在客户端或服务端实现**多源数据拉取、去重、时间戳排序**的逻辑。
- 分页、滚动加载时，要处理跨多个发件箱的游标和边界问题，实现难度比推模式更高。

 4. **存储与一致性问题**

- 发件箱需要长期保存，**存储成本较高**（不像推模式只存收件箱）。
- 内容删除 / 修改时，需要同步更新所有拉取过该内容的场景，**一致性维护更复杂**。

## Feed流的实现方案2

**推模式**：也叫做写扩散

![image-20260319145732117](/images/黑马点评/image-20260319145732117.png)

博主发布内容后，立即将这条内容**推送给所有粉丝的收件箱**，用户刷 Feed 时直接读取自己的收件箱即可。

1. **写放大问题严重**

- 当博主发布一条内容时，需要将这条消息**写入所有粉丝的收件箱**。
- 如果是百万、千万级粉丝的大 V，一次发博就会触发**百万级甚至千万级的写入操作**，对**数据库和缓存的写入压力极大**，容易造成系统延迟甚至雪崩。
- **粉丝越多，写放大效应越明显**，成为系统的性能瓶颈。

2. **存储成本极高**

- 同一条内容会被冗余存储在**所有粉丝的收件箱**中，数据量会随着粉丝数呈线性增长。
- 例如，一条内容被 100 万粉丝关注，就会产生 100 万条冗余数据，极大增加了存储开销。

3. **热点与延迟问题**

- 大 V 发博时会瞬间产生海量写入请求，容易形成**写入热点**，导致其他用户的正常操作被阻塞。
- 粉丝数越多，推送完成的时间越长，部分粉丝可能会**延迟很久才能看到新内容**。

4. **内容变更 / 删除复杂**

- 当博主删除或修改已发布的内容时，需要遍历**所有粉丝的收件箱**去更新或删除这条消息，操作成本极高且难以保证一致性。
- 极端情况下，可能出现部分粉丝已经看到旧内容，而另一部分还没收到推送的不一致状态。

5. **新关注用户的历史数据问题**

- 新用户关注博主后，无法自动获取该博主的**历史内容**，需要额外实现 “拉取历史” 的逻辑来补全收件箱，增加了系统复杂度。

## Feed流的实现方案3

**推拉结合模式**：也叫做读写混合，兼具推和拉两种模式的优点。

![image-20260319150802018](/images/黑马点评/image-20260319150802018.png)

推拉结合模式是为了规避纯推 / 纯拉模式的缺陷而设计的，核心思路是**对不同类型的博主 / 用户采用不同策略**：

- 普通用户：走**拉模式**，粉丝少，写放大可控，读性能好。
- 大 V / 头部博主：走**拉模式**，只存发件箱，避免百万级粉丝的写放大，用户刷流时再拉取其内容。
- 活跃粉丝：可能会**优先推送**，保证体验；非活跃粉丝则按需拉取。

### 优点

1. **缓解写放大与读放大**

   - 大 V 内容不推送给所有粉丝，避免了纯推模式下的极端写放大。

   - 普通用户内容仍走推送，保证大部分用户刷流时是纯读自己的收件箱，避免纯拉模式下的大量读请求。

2. **性能与成本更均衡**

   - 存储上，大 V 内容只存一份在发件箱，避免了冗余存储；普通用户走推送，整体存储成本可控。

   - 系统负载更均匀，不会因大 V 发博而瞬间打满写入能力。

3. **灵活性高**

   - 可根据粉丝量、活跃度、内容类型动态调整推拉策略，比如对百万粉大 V 走拉模式，对万粉以下博主走推模式。

   - 新关注用户可拉取大 V 历史内容，同时推送普通用户的新内容，兼顾一致性与体验。

### 缺点

1. **实现复杂度大幅提升**

   - 需要维护两套逻辑：推模式的收件箱写入、拉模式的发件箱读取，还要做**推拉策略的判断与切换**。

   - 要处理混合场景下的合并排序、分页、去重等问题，代码和架构更复杂。

2. **延迟与一致性问题**

   - 拉取大 V 内容时，仍会产生一定读请求，在用户关注大 V 多的情况下，读延迟会比纯推模式略高。

   - 大 V 内容删除 / 修改时，虽然不用遍历所有粉丝收件箱，但需要在拉取时做校验，一致性维护仍有成本。

3. **缓存与热点问题**
   - 大 V 的发件箱会成为热点，被大量粉丝频繁拉取，需要做更精细的缓存分层和热点隔离，否则容易出现缓存击穿。

4. **运维与监控成本高**
   - 系统链路更长，需要同时监控推、拉两种路径的性能、延迟和异常，运维复杂度高于单一模式。

|              |  拉模式  |      推模式       |       推拉结合        |
| :----------: | :------: | :---------------: | :-------------------: |
|    写比例    |    低    |        高         |          中           |
|    读比例    |    高    |        低         |          中           |
| 用户读取延迟 |    高    |        低         |          低           |
|   实现难度   |   复杂   |       简单        |        很复杂         |
|   使用场景   | 很少使用 | 用户量少、没有大V | 过千万的用户量，有大V |

    /**
     * 保存博文
     *
     * @param blog
     * @return
     */
    @Override
    public Result saveBlog(Blog blog) {
        // 1.获取登录用户
        UserDTO user = UserHolder.getUser();
        blog.setUserId(user.getId());
        // 2.保存探店博文
        boolean isSuccess = save(blog);
        if (!isSuccess) {
            return Result.fail("新增笔记失败！");
        }
        // 3.查询笔记作者的所有粉丝
        List<Follow> follows = followService.query().eq("follow_user_id", user.getId()).list();

        // 4.推送笔记id给所有粉丝
        for (Follow follow : follows) {
            // 4.1.获取粉丝id
            Long userId = follow.getUserId();
            // 4.2.推送
            String key = "feed:" + userId;
            stringRedisTemplate.opsForZSet().add(key, blog.getId().toString(), System.currentTimeMillis());
        }
        // 4..返回id
        return Result.ok(blog.getId());
    }

    /**
     * 查询用户
     *
     * @param max
     * @param offset
     * @return
     */
    @Override
    public Result queryBlogOfFollow(Long max, Integer offset) {
        // 1.获取当前用户
        Long userId = UserHolder.getUser().getId();

        // 2.查询收件箱 ZREVRANGEBYSCORE key  MAX MIN  LIMIT offset count
        String key = FEED_KEY + userId;
        Set<ZSetOperations.TypedTuple<String>> typedTuples = stringRedisTemplate.opsForZSet().reverseRangeByScoreWithScores(key, 0, max, offset, 3);

        // 3.非空判断
        if (typedTuples == null || typedTuples.isEmpty()) {
            return Result.ok();
        }

        // 4.解析数据 blogId、score(时间戳)、offset
        List<Long> ids = new ArrayList<>(typedTuples.size());
        long minTime = 0;
        int os = 1;
        for (ZSetOperations.TypedTuple<String> tuple : typedTuples) {
            // 4.1.获取id
            ids.add(Long.valueOf(tuple.getValue()));

            // 4.2.获取分数(时间戳)
            long time = tuple.getScore().longValue();
            if (minTime == time) {
                os++;
            } else {
                minTime = time;
                os = 1;
            }
        }

        // 5.根据id 查询blog
        String idStr = StrUtil.join(",", ids);
        List<Blog> blogs = query().in("id",ids).last("ORDER BY FIELD(id," + idStr +")").list();

        blogs.forEach(blog -> {
            // 5.1.查询blog有关的用户
            queryBlogUser(blog);
            // 5.2.查询blog是否被点赞
            isBlogLiked(blog);
        });


        // 6.封装并返回
        ScrollResult r = new ScrollResult();
        r.setList( blogs);
        r.setOffset(os);
        r.setMinTime(minTime);

        return Result.ok(r);
    }
```

保存博文的思路：

- 首先我们需要获取到当前用户的id
- 根据前端传回来的参数，我们对blog进行封装用户id并且加载到数据库中
- 当我们保存了博文之后，我们根据被关注也就是`follow_user_id`列进行查询，获取关注我们的粉丝信息
- 推送笔记id给所有粉丝，然后使用redis保存下来并且返回笔记id(相当于发到收件箱中)

推送博文的思路：

- 当用户需要查看自己关注博主的博文时候，获取当前登录用户的id

- 使用`ZREVRANGEBYSCORE`滚动的查询收件箱(`feed:userId`)

  - 返回有序集合中指定分数区间内的成员，分数由高到低排序。

  - 完整示例：`ZREVRANGEBYSCORE key max min WITHSCORES LIMIT offset count`

    - |       指令       | 是否必须 |                          说明                           |
      | :--------------: | :------: | :-----------------------------------------------------: |
      | ZREVRANGEBYSCORE |    是    |                          指令                           |
      |       key        |    是    |                     有序集合键名称                      |
      |       max        |    是    |               最大分数值,可使用”+inf”代替               |
      |       min        |    是    |               最小分数值,可使用”-inf”代替               |
      |    WITHSCORES    |    否    |                   将成员分数一并返回                    |
      |      LIMIT       |    否    | 返回结果是否分页,指令中包含LIMIT后offset、count必须输入 |
      |      offset      |    否    |                    返回结果起始位置                     |
      |      count       |    否    |                      返回结果数量                       |

- 解析数据 blogId、score(时间戳)、offset
  - 解析博客id，由于ArrayList的初始容量只有10，如果我们的内容很多的话，就需要提前定义同时节省内存(精确分配所需空间，避免浪费)，提高效率（知道确切大小后一次性分配，比动态扩容更高效）
  - 然后获取时间戳和偏移量(os)，设置时间戳的作用是防止如果同一时间添加数据就可以进行偏移量的设置
    - 根据TypedTuple存储的值，遍历`tuple`数组通过`getValue()`获取ids，然后通过`getScore()`获取时间戳，通过判断前后时间戳是否相等对偏移量进行设置

```java
    public interface TypedTuple<V> extends Comparable<TypedTuple<V>> {
        @Nullable
        V getValue();

        @Nullable
        Double getScore();
    }
```

- 根据id，查询blog
  - 通过`StrUtil.join(",", ids);`来拼接ids，然后通过`ORDER BY FIELD`来查询数据
  - 最后遍历博客来查询博客有关的用户信息并且判断是否点赞
