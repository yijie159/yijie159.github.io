# Redis复制<!--more-->

Redis的每个主实例都有一个**复制ID和一个偏移量**。这两条数据对于确定副本可以继续其复制过程的时间电点或确定它是否需要进行完整同步至关重要。

当Redis副本实例仅**落后于主实例几个偏移量**时，他会从主实例接受剩余的命令，然后在其数据集上重放，直到同步完成。如果两个实例无法就复制ID达成一致，或者主实例不知道偏移量，则副本将请求全量同步。

![poc](/images/黑马点评/主从复制.png)

## 完整流程

1. **触发**：从库发送 `PSYNC` 请求，带上自己最后的偏移量。
2. **决策**：主库判断该偏移量是否还在复制缓冲区内。
   - 如果在 → 走**增量复制**（只发差异命令）。
   - 如果不在（或首次） → 走**全量复制**。
3. **全量复制三步走**：
   - **拍快照**：主库执行 `bgsave`，生成 RDB 文件（这是数据的“全量骨肉”）。
   - **记录变化**：在生成 RDB 的同时，主库把期间的新增命令缓存在缓冲区，并记录起始偏移量。
   - **发送与追赶**：主库先发 RDB，从库加载；发完 RDB 后，主库再发缓冲区里的增量命令。从库执行完这些命令后，偏移量才真正追上。

偏移量只是主从双方在TCP连接中用来**核对进度**的一个数字，类似于“我们已经同步到第几条指令了”。

##  关于“快照生成截止偏移量”的解读

主库生成RDB快照的那一刻，会记下一个“截止偏移量”。生成快照期间，新的写请求来了，偏移量变成了“当前偏移量”。**这两者之间的差值，就是快照期间产生的增量数据**。

## “新主库记住旧复制ID”是怎么回事？（故障转移的关键）

- **场景**：假设主库A挂了，从库B被**提升（晋升）**为新的主库。
- **此时发生的事**：Redis会给B分配一个**全新的复制ID**（因为B现在是一本新“书”的作者了）。
- **精妙之处**：B虽然有了新ID，但它会**把旧主库A的复制ID记在心里（存为旧ID）**。
- **好处**：此时，另一个从库C（原来也同步于A）来找B同步。C带的复制ID还是旧的（A的ID）。
- **B的判断**：B一看，“咦，你带的这个旧ID，我刚好记得！咱俩有共同祖先！”于是，B就用旧ID对应的偏移量进行计算，发现只需要把C缺失的那几百条指令发过去就行了——**这就避免了昂贵的全量同步**。

# Redis哨兵

Sentinel的设计方式是，一组哨兵进程协同工作以协调状态，从而为Redis**提供高可用性**。保护免受故障影响的系统有自己的单点故障，因此**主从复制**解决了**数据备份和读扩展**的问题而哨兵则是在主从复制的基础上，解决了故障自动切换的问题(即：主库挂了怎么办)。

## 哨兵到底是干什么的？

Sentinel是一个**独立于Redis数据存储之外的进程集群**。它不是一台，而是一组（至少3台），主要做四件事：

- **监控**：哨兵们不断问主库和从库“你还活着吗？”（Ping）。
- **通知**：如果某台挂了，发警报给管理员。
- **故障转移**：如果主库真的死了，哨兵们投票选出一个从库，把它提升为新主库。
- **配置管理**：哨兵充当“导游”。客户端想写数据时，先问哨兵“现在谁是新主库？”哨兵告诉客户端新地址。

## 什么是“Quorum(法定票数)”？

“Quorum”和“Tolerated Failures（容忍故障数）”是哨兵**做出正确决策**的关键。

- **Quorum**：指的是**判定主库“真的挂了”所需要的最少同意票数**。
- **为什么需要它？** 假设网络抖动，只有*1个哨兵觉得主库连不上，但主库实际是好的*。如果听信这1个哨兵就切换，会造成“脑裂”或无故切换。所以需要**多个哨兵共同确认**。

**正确的生产经验值**是：

- **Quorum = (总哨兵数 / 2) + 1**（即多数派）

## 故障转移的完整流程

1. **主观下线**：1个哨兵Ping不通主库，觉得它可能挂了（主观）。
2. **客观下线**：该哨兵问其他哨兵，如果达到**Quorum**（如3台里的2台）都认为主库挂了，就判定为客观下线。
3. **选举领袖**：哨兵们内部再选出一个“领导哨兵”来执行切换。
4. **选新主库**：领导哨兵从所有从库里，选一个**复制偏移量最大**（数据最新）的从库，执行 `slaveof no one` 提升为主库。
5. **改换门庭**：领导哨兵让其他从库去复制这个**新主库**（这会触发之前提到过的“复制ID变更与继承”逻辑）。
6. **更新配置**：哨兵更新自己的配置，并通知客户端新主库地址。

***以下是我的理解***：由于主从复制，如果主库挂了，那么就会把数据备份，哨兵发现主库真的死了之后，就来吧这个从库升成主库，用来解决故障转移

## 谁来成为执行者？哨兵宕机导致无法过半又怎么解决？

哨兵谁来成为执行者来让从库升为主库？这里使用的核心规则如下：

- **毛遂自荐（发起选举）**：最先发现主库死亡的哨兵A，会给自己投一票，并向B和C广播：“我要当Leader，选我！”
- **先到先得（投票规则）**：B和C收到请求后，遵循**“First Come, First Served（先来先得）”**原则。
  - 在一个“选举周期”内，B和C**只能投给第一个向它们拉票的哨兵**。
  - 比如B先收到A的请求，B就投A一票；紧接着C也收到A的请求，C也投A一票。
- **过半数获胜（获胜条件）**：**必须获得超过半数的票数**（即 `N/2 + 1`）才能当选Leader。
  - 如果A获得了3台里的2票，A获胜，由A执行后续的故障转移。
  - 如果平票（比如3台各投自己），则等待随机时间后重新发起选举，直到选出Leader为止。

但是这里的先到先得要**注意**：如果最先发现的哨兵A在拉票时网络延迟较大，或者它自己的状态不够健康，而哨兵B稍晚但网络更好，那么B可能率先收到足够多的“同意票”而成为Leader。所以，**“先发现”只是占得先机，最终拍板权归于“先凑齐过半选票”的哨兵**。

### 关于“哨兵宕机导致无法过半”——这是分布式系统经典难题

Redis官方**强烈建议部署至少3个哨兵，并且最好是奇数个**。

**场景**：假设你部署了 **2个哨兵**（哨兵A和哨兵B），Quorum设置为2（必须2票才能判定主库死亡）。

- 某天，**哨兵A自身宕机**了（或者网络隔离）。
- 接着，真正的Redis主库也挂了。
- 此时只剩下哨兵B还活着。B试图发起故障转移，但它只能获得**自己投给自己的1票**。
- 因为总共只有2个哨兵，**B永远凑不齐“过半”**（需要超过1票，即2票）。于是，**选举流程一直阻塞，永远无法选出Leader**，故障转移彻底失败——你的Redis服务虽然后台有从库，但无人将其晋升，系统对外不可写，陷入**死锁**。

### Redis的保底措施（但无法完全解决死锁）

Redis 在哨兵配置中有一个参数：`down-after-milliseconds`（判定主库超时时间）。如果哨兵长时间无法选举出Leader，它会**不断重试**，每次重试前等待一个随机时间（避免多个哨兵同时拉票造成反复平票）。

但**如果活着的哨兵数量本身就不过半，再怎么重试也没用**，因为数学规律不可打破——票数不够。

# Redis集群

“主从复制”是备份、“哨兵”是自动换备胎，那么**Cluster**解决的是**“一台机器装不下所有数据”**的问题

### 数据到底怎么分散？（分片 vs 取模）

图上提到了“算法分片”和“取模”的老办法，并指出了它的痛点。

- **老办法（取模）**：假设有3台机器，存一个key时，计算 `hash(key) % 3`，决定存哪台。
- **致命缺陷**：如果后来加了1台机器，变成4台，公式变成 `% 4`。**绝大部分key的计算结果都变了**，意味着几乎所有数据都要在机器间搬迁（大规模数据迁移），这在生产上是灾难。

### 集群成员间怎么通信？（Gossip 协议）

![图片](https://cdn.xiaolincoding.com//picgo/c98d7da88a22fc53bcf6110fd4f3839e-20251008001717022.jpeg)

图上最后提到了 **Gossip（流言）协议**。Cluster中每个节点都知道其他节点的存在，但它们是怎么同步信息的呢？

**答案：就像办公室里传八卦一样。**

- **每个节点每隔一段时间，随机找几个“朋友”（其他节点）聊几句**：“我这边状态正常”、“我听说M3好像挂了”。
- 这种随机、去中心化的传播方式，让**节点状态（谁活着、谁负责哪些槽）**能很快传遍整个集群。

**Gossip的好处**：不依赖中心化的“总司令”（无中心节点），避免了单点故障。**代价**：信息传播有秒级延迟（不是强一致的）。

# Redis持久化模型

## 无持久化

如果你愿意，可以完全禁用持久化。这是运行 Redis 的最快方式，并且没有持久性保证。

## RDB文件

RDB（Redis 数据库）：RDB 持久化以指定的时间间隔执行数据集的时间点快照。

这种机制的**主要缺点**是快照之间的数据会丢失。此外，这种存储机制还依赖于主进程的 fork，在更大的数据集中，这可能会导致服务请求的瞬间延迟。话虽如此，RDB 文件在内存中的加载速度要比 AOF 快得多

## AOF

AOF（Append Only File）：AOF 持久化记录服务器接收到的每个写入操作，这些操作将在服务器启动时再次被执行，重建原始数据集。

这种持久性的方法能够确保比 RDB 快照更持久，因为它是一个仅附加文件。随着操作的发生，我们将它们缓冲到日志中，但它们还没有被持久化。该日志与我们运行的实际命令一致，以便在需要时进行重放。

然后，如果可能，我们使用 fsync 将其刷新到磁盘（当此运行可配置时），它将被持久化。缺点是格式不紧凑，并且比 RDB 文件使用更多的磁盘。
